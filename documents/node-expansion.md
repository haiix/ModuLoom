# 基本ノード拡張と可変入力の方針

## 代表シナリオと採否

候補は「既存ノードを不自然に組み合わせず、安全な組み込み処理として繰り返し使うか」を基準に
評価します。今回の採用7件はCoreへ追加し、保存形式を変更しません。

| シナリオ                       | 候補                                    | 判断                             | 理由                                                                          |
| ------------------------------ | --------------------------------------- | -------------------------------- | ----------------------------------------------------------------------------- |
| UI入力を許容範囲へ収める       | Math min / max / clamp                  | Clampを追加、min / maxは据え置き | Clampが範囲制限を1ノードで表し、単独min / maxは実利用例を待つ                 |
| 入力文字列を正規化する         | trim / lowercase                        | Trimを追加、lowercaseは据え置き  | 前後空白除去はフォーム処理の境界で頻出。小文字化はUpperCaseと自作式で代替可能 |
| 配列から1件を選ぶ              | get item                                | 追加                             | Sliceでは配列のままで、要素を取り出す安全な標準手段がない                     |
| オブジェクトの項目を列挙する   | keys                                    | 追加                             | Get Propertyはキーが既知の場合だけで、反復や検査へつなげられない              |
| フォーム値を計算値へ変換する   | to number                               | 追加                             | 暗黙変換を各演算ノードへ散らさず、失敗を `INPUT_TYPE` で可視化できる          |
| 汎用値を表示文字列へ変換する   | to string                               | 追加                             | 文字列ノードへの明示的な境界になり、型配線を維持できる                        |
| 実行中のJSON文字列を値へ戻す   | parse JSON                              | 追加                             | JSON Inputは状態sourceであり、上流の文字列を変換できない                      |
| 比較条件を増やす               | less / less-or-equal / greater-or-equal | 据え置き                         | Greaterの入力反転、Equal、Logicの組み合わせで表現できる。実例を収集する       |
| 文字列を検索・置換する         | contains / replace                      | 据え置き                         | 大文字小文字、全置換、正規表現など契約の選択を先に決める必要がある            |
| 配列を整列・重複排除する       | sort / unique                           | 据え置き                         | 要素型と比較規則がない現行のflatなarray型では契約が曖昧になる                 |
| オブジェクトを結合する         | merge                                   | 据え置き                         | キー競合、深い結合、危険キーの扱いを利用例から決める必要がある                |
| 入力数を実行時に増減する       | Concat / Combine Items / Wait for All   | 据え置き                         | 配列入力を優先し、動的port IDの保存契約を先に設計する                         |
| 任意個の値を埋め込む           | Template                                | 据え置き                         | キー付きobject入力の専用ノードとして再検討する                                |
| Array / Stream設定を共通化する | Map / Filter                            | 据え置き                         | 同期配列とAsyncIterableで実行・キャンセル契約が異なる                         |
| ノード固有UIを減らす           | メタデータ駆動フォーム                  | 別Issue候補                      | 可変入力と独立して段階移行し、既存stateの互換性を検証する                     |

追加ノードは型変換の境界または単一責務の基本操作であり、自作式を使わない利用者にも発見可能で、
実行時とTypeScript生成で同じ成功・失敗契約を持ちます。詳細は
[ノード実行契約](./node-contract.md)を参照してください。

## 可変入力ポート

現行1.xでは可変入力ポートを導入しません。ポート配列はノード定義の一部であり、ノードインスタンス
ごとに増減させると、ポートID、接続、Undo、複合ノード境界、プロジェクト読込検証、TypeScript生成の
全経路へ新しい状態モデルが必要になります。

同種の値をまとめる用途では、まず配列を可変長コンテナとして使います。

- 文字列の可変連結はArray Joinを使う。
- 値の可変集合は複数のCombine Itemsを重ねるか、配列sourceを使う。
- Templateの `{a}` / `{b}`、Wait for Allの2入力は互換性維持のため据え置く。
- Promise配列、任意キーのTemplate、動的フォームで明確な利用例が揃った時点で専用の配列入力
  ノードを先に検討する。

将来可変ポートを導入する場合は、`NodeInstance` に `dynamicPorts` を持たせ、安定したport IDと表示順を
保存します。NodeDefinitionは最小件数、最大件数、追加可能方向、型を宣言します。評価エンジンは定義と
インスタンスのポートを合成し、読込時には接続先ID、重複、上限を検証します。コード生成は表示順では
なく保存されたport ID順を使います。旧インスタンスには固定ポートを補い、project versionを上げて
往復互換テストを追加します。

## UI・保存・コード生成への影響

今回の7件は既存の固定ポートUIをそのまま使い、Utilityを含む既存カテゴリに表示します。新しい
`typeId` だけが増え、既存プロジェクト、既存ノード、`FlowProjectExport 1.1.0` は変更しません。
旧アプリが新ノード入りプロジェクトを読めない点は、従来の未知typeIdと同じversion境界です。

ランタイム実装と `BUILTIN_NODE_CODEGEN` を同時に追加し、全組み込みノードのコード生成同等性テスト
へ含めます。ノードごとのハードコードUIをメタデータ駆動へ移す案は、可変ポートと独立したUI基盤の
変更として据え置きます。

## 優先順位とテスト観点

採用した7件をP0として同時に提供します。次の候補は利用シナリオが確認できた順に、contains / replace、
比較3種、min / max、sort / unique、mergeの順で再評価します。

テストでは、通常値に加えて次を確認します。

- Clampの上下境界と `min > max`
- Trimの内部空白維持
- Get Itemの先頭、末尾、負数、整数制約、範囲外
- Object Keysが継承プロパティを含めないこと
- To Numberの有限数と変換不能値、To Stringのboolean等
- Parse JSONのobject / array / primitiveと構文エラー
- 全組み込みノードのランタイムとTypeScript生成の出力・エラー同等性
- カタログ検索、分類、既存プロジェクト読込の回帰
