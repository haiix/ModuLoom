# 型システム設計

## 責務と保証範囲

ModuLoomのポート型は、編集時の配線候補と不正接続の防止、およびノード入力直前の基本的な
実行時検査を担います。TypeScriptの静的型検査器やJSON Schemaの代替ではありません。

型には二つの保証レベルがあります。

- 組み込み型は値の外形を検査します。`number` は有限数、`array` は配列、`object` は `null` と
  配列以外のオブジェクト、`promise` はthenable、`stream` はAsyncIterableです。
- カスタム型は配線時には型IDによるnominal型として扱い、通常のポート入力ではプレーン
  オブジェクトであることだけを確認します。フィールド構造の保証が必要な箇所では、その型から
  生成されたValidateノードを通します。

ノードは入力契約に合わない実行値を `INPUT_TYPE` として拒否します。配線可能であっても、`any`
から流入した値などは実行時に拒否される場合があります。型に合うことは業務上の意味、値域、文字列
形式、オブジェクトの追加プロパティまで正しいことを意味しません。

## 現行の型表現

現行1.xでは保存済みポートの文字列型を維持し、次は導入しません。

- `array<number>`、`Promise<User>`、`Stream<number>` のようなジェネリック型
- nullable、union、`unknown`
- カスタム型フィールドから別のカスタム型を参照するネスト

現在のArray / Promise / Streamノードには要素型を保存・伝播する契約がなく、文字列だけを拡張すると
UI上の精度とランタイム保証が乖離します。また、ネスト型には循環参照、既定値、削除、サンプル依存物、
TypeScript interfaceの出力順を同時に設計する必要があります。このため、要素型を実際に保持する
ノード契約と構造化された型参照を用意できる段階まで留保します。

## 接続互換性

| 出力               | 入力       | 判定 | 理由                                           |
| ------------------ | ---------- | ---- | ---------------------------------------------- |
| 同じ型             | 同じ型     | 許可 | 通常の接続                                     |
| 任意               | `any`      | 許可 | 汎用sinkとの既存互換                           |
| `any`              | 任意       | 許可 | 動的sourceとの既存互換。入力時に再検査         |
| 登録済みカスタム型 | `object`   | 許可 | カスタム値はプレーンオブジェクトとして利用可能 |
| `object`           | カスタム型 | 拒否 | フィールド保証がない。Validateを明示的に使用   |
| 異なるカスタム型   | カスタム型 | 拒否 | 型IDによるnominal型                            |

`any` の双方向互換は既存グラフ、自作ノード、Inspectorを壊さないため1.xでは維持します。
`unknown` は導入していないため、Validateの入力など動的データの境界には引き続き `any` を使います。

## カスタム型とValidate

カスタム型編集UIで選べるフィールド型は `number`、`string`、`boolean`、`array`、`object`、`any`
です。Validateは次をすべて満たす場合だけ `isValid: true` と型付き `instance` を返します。

1. 入力が `null` と配列以外のオブジェクトである。
2. 必須フィールドが `null` / `undefined` ではない。
3. 存在する必須・任意フィールドの値が宣言された組み込み型に合う。

未知の追加プロパティは許可します。Validateは外形検査であり、再帰的なJSON Schema検査や文字列形式、
数値範囲の検査ではありません。ランタイムとTypeScriptコード生成は同じ判定を実装します。

Constructor / Deconstruct / Validateは、教材サンプル由来ならExamples、ユーザー定義ならProjectへ
配置します。機能カテゴリはConstructor / DeconstructがObject、ValidateがLogicです。

## 保存形式とコード生成

今回の決定では `DataType` と `CustomTypeField.type` の文字列表現を変えないため、プロジェクト形式は
`1.1.0` のままです。既存プロジェクトは移行なしで読み込めます。Validateの `typeId`、ポート、
ノードインスタンスも変更しません。既存Validateは同じグラフのまま、値の型まで検査する強い契約へ
更新されます。

TypeScript生成はカスタム型を従来どおりinterfaceとして出力し、Validateにはアプリ内実行と同じ
外形検査を埋め込みます。ジェネリック型を導入していないため、現在の `any[]`、Promise、Streamの
生成表現は変わりません。

## 将来の段階的移行案

ジェネリック型を導入する場合は、一度に保存文字列を書き換えず次の順に進めます。

1. `string` 型を読み取れるまま、`TypeRef`（nameとtype argumentsを持つ構造）を内部表現へ追加する。
2. Array / Promise / Streamノードに要素型の推論・保持・表示を追加し、型引数なしは `unknown` 相当とする。
3. 互換判定、色、候補順位、複合ノード境界、カスタム型参照を構造化型へ対応させる。
4. TypeScript生成とプロジェクト形式を新versionへ上げ、旧文字列を無損失で移行する。
5. 十分な読み書き往復期間の後にだけ、旧形式の新規書き出しを停止する。

検証では、旧版ファイルの読み込み、旧→新→保存→再読込、型引数の一致・不一致、`any` / `unknown`
境界、カスタム型からobjectへの方向性、ネストと循環参照、複合ノード、全組み込みノードのランタイム
と生成コードの同等性を必須観点とします。
